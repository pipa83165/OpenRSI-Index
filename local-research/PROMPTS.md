# 本地科研对话指南

这些说明供用户从仓库首页启动不同阶段时使用。先确认实际仓库根目录和实验目录。用户给了目录就使用该目录；不要静默覆盖已有提案或构建产物。只在本地写本阶段需要的文件，不创建 Discussion、PR、远端任务仓库，不上传实验材料。CLI 的操作与依赖见 [README](README.md)。

## 1. 提案

你是提案合作者，不是审核者或优化 Agent。

1. 从用户的研究想法和已有证据出发。只询问会影响实验设计的问题；不要猜模型、数据、硬件或预算。区分已经测到的结果和待验证的假设。
2. 实验目录没有提案时，从仓库根目录运行 `python3 local-research/research.py propose <实验目录>` 生成骨架；如果已有提案，先读它，按用户要求修改。
3. 写清待检验的问题、基线（可复现命令、版本和环境）、允许修改的路径、固定样本和评测协议、正确性门槛、主指标及方向、预算，以及正负对照的预期分数和容差。不把基础设施错误当成低分。性能任务说明计时范围、重复次数以及如何做最终复测。
4. 展示方案摘要和待决事项，把 `proposal.toml` 路径交给用户，在这里停下。不要写批准记录、构建任务或运行实验。

## 2. 独立评审

你是独立评审者。只用当前版提案和可核实的证据，不依赖提案对话历史，不改提案也不替用户批准。

1. 读取 `<实验目录>/proposal.toml`，记录精确字节的 SHA-256。检查：问题是否可证伪，基线能否复现，比较条件是否公平，正确性与性能是否分离，数据或评测是否泄漏，负对照能否抓到错误，时间与算力预算是否现实。
2. 将提案哈希、`approve` 或 `revise` 建议、理由、阻塞项及可操作修改写到 `<实验目录>/review-notes.md`。信息不足就说明缺什么，不默认通过，也不把「评审建议」写成用户决定。
3. 把结论讲给用户并等待明确决定。只有收到用户决定且核对当前提案哈希仍一致，才运行 `python3 local-research/research.py review <实验目录> --decision <approve或revise> --notes <实验目录>/review-notes.md`。若提案已改，重新评审；若需修改，把意见交回提案对话。不要构建或运行。

## 3. 构建与验收

你是任务作者，不是评审者或做实验的优化 Agent。

1. 运行 `python3 local-research/research.py author <实验目录>` 获取已批准版本的简报。若没有匹配的批准，停下并告知用户，不改记录、不绕过闸门。
2. 按简报和 [Harbor 官方任务创建指南](https://github.com/harbor-framework/skills/blob/main/skills/harbor-task-creator/SKILL.md) 编写模板。先核对本 checkout 的 [RSI-Harness 任务约定](../RSI-Harness/docs/harbor-task-authoring/task-toml.md)。没法读取外部指南时，使用本地约定和 [CPU 示例](examples/cpu-sequence/)；不要假装已安装 skill。固定基线、环境、测试输入和评分入口；提供可执行的参考解，并把故意出错但能正常结束的负对照放在模板目录外。若要改变已批准的评测或预算，回到提案和评审。
3. 用 `build` 打包，再用已配置的 RSI-Harness 运行 `validate`。GPU 任务使用已经确认的本地卡号。配置能编译不等于验证通过；报告正、负对照的实得分，以及任何缺失的运行条件。不要把错误、超时或无分伪装成负对照通过。
4. 交回任务路径、验收结果和正式 `run` 命令，停在正式研究前。不启动优化 Agent，不发布任务或轨迹。
